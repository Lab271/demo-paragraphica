# Terra Virtualis — Rebuild Plan (September 2026)

Assessment of the 2024 codebase and a phased plan to modernise it, with a
local-first inference option. Issues track each phase.

## Where we are

A 2024 pipeline: Streamlit sidebar → Mapbox reverse geocode → OpenWeatherMap →
geotimezone → GPT-4 writes a location description → string-concatenated prompt
→ DALL-E 3. On the Raspberry Pi it runs as a Streamlit server under systemd with
Chromium in kiosk mode pointed at localhost.

Problems:

- Five network calls and three API keys per image.
- Prompt is built by string glueing; no way to inspect or test it in isolation.
- No persistence beyond a single `output/output.png`.
- Streamlit reruns the script on every widget change, so geocoding fires on
  every keystroke. Only the Generate button should trigger work.
- Streamlit on the Pi needs a browser, an X session and a 15 s boot sleep to
  display one picture.
- Rotary encoders, display controller, camera and wifi from the README todo
  were never built.
- Packaging is virtualenv + hand-rolled pip lines in the Makefile; Ansible
  copies three Python files one by one because Python on ARM is painful.

## Target architecture

```
+------------------+        HTTP         +------------------------------+
|  Pi (camera)     | ------------------> |  Mac Mini (inference node)   |
|  GPIO / dial     |  location, style    |  FastAPI service             |
|  framebuffer     | <------------------ |  core: Location+Style ->     |
|  GPS or fixed    |  image + prompt     |        Prompt -> Image       |
+------------------+                     |  backends: cloud | local     |
                                         |  JSONL history + images      |
                                         +------------------------------+
                                                   ^
                                                   |  CLI (dev loop)
                                            terra generate --location ...
```

- **Core** is a pure function `Location + Style + Context -> Prompt -> Image`,
  tested with recorded fixtures (the JSON files in `tests/` already exist).
- **Backends** share one interface. `cloud` = OpenAI GPT Image 2 (drop-in for
  DALL-E 3, same SDK). `local` = Ollama for the description + Draw Things or
  mflux for the image, running on the Mac Mini. Switched by config.
- **Geo context** goes offline where possible: timezone via `timezonefinder` +
  `zoneinfo` (removes one API key). Reverse geocode and weather stay remote,
  wrapped in a `Context` dataclass so the model layer never sees raw API JSON.
- **Persistence**: every generation writes image + prompt + revised prompt +
  location + style to `output/` with a JSONL index. The demo value is
  comparing places and styles; today that history is lost per click.
- **UI by role**:
  - Laptop dev loop: Typer CLI with `--dry-run` (prints description + prompt,
    spends no image call).
  - Pi device: pygame/framebuffer + GPIO. No browser, no X.
  - Audience: static gallery over the JSONL history, or the device screen.
  - Optional control: the FastAPI service itself.
- **Packaging**: `uv` with full `pyproject.toml` and lockfile. `requirements.txt`
  and the Makefile pip lines go. Ansible does `git checkout` + `uv sync`.
  1Password lookups for keys stay.

Streamlit, the `mapbox` SDK and the Chromium kiosk are removed.

## Image model choice

Imagen was shut down in Aug 2026; Gemini Flash Image is the direct backend.
OpenRouter's unified Image API (#38) puts the rest behind one key, so the model
is a per-picture choice. Live test 2026-09-22, same film-noir Westerkerk prompt,
3:2, cheapest quality that the model accepts:

| Model (OpenRouter slug) | s | $/image | Verdict |
|---|---|---|---|
| `openai/gpt-image-2.5-flare` low | 12 | 0.005 | clean noir, real Westerkerk, best value; the default |
| `openai/gpt-image-2` low | 13 | 0.005 | as above, slightly flatter |
| `black-forest-labs/flux.2-pro` | 20 | 0.045 | most photographic, real rain; bridge to local (#8) |
| `bytedance-seed/seedream-4.5` 2K | 8 | 0.04 | dramatic low angle; rejects 1K |
| `google/gemini-3.1-flash-image` 1K | 13 | 0.067 | identical to direct Gemini |
| `black-forest-labs/flux.2-klein-4b` | 4 | 0.015 | fastest, church invented |
| `microsoft/mai-image-2.6-flash` | 11 | 0.016 | painterly HDR, church partly invented |
| `qwen/qwen-image-3` 1K | 84 | 0.03 | good but not b/w; one 120 s timeout |
| `x-ai/grok-imagine-image-2.0` low | 15 | 0.04 | sepia, ignored b/w |
| `recraft/recraft-v4.1` 4:3 | 6 | 0.035 | illustration feel, no 3:2 |

Local-first reality: the Pi 5 cannot generate acceptable images even with the
AI HAT+ 2 (SD 1.5 at 512 px, tens of seconds, thermal throttling). A Mac Mini
with 24 GB does a 1024 px Flux image in ~50 s; Flux schnell 4-bit is 15–30 s on
M2 Ultra / M3 Pro. Draw Things is the fastest engine on Apple Silicon and
exposes an HTTP API. So the split is: Pi as thin client, Mac as inference node,
cloud as fallback.

Trade-off: local is slower and a step below frontier quality, especially for
the "lego box set" / "pop-up card" styles. Gain: runs with no wifi, costs
nothing per click, and the story is closer to Karmann's original.

## Language

Python for the pipeline: it is HTTP glue, and Rust buys nothing there. Rust only
for the Pi client, and only in phase 3: a single cross-compiled binary (`rppal`
for GPIO, framebuffer output, one POST) removes the whole ARM-Python deployment
problem. If phase 3 never happens, pygame on the Pi is fine and nothing is lost.

## Phases

1. **Core + cloud backend + CLI** (Python). Smallest change to existing code.
   Unblocks everything else.
2. **Packaging + deploy**: uv, lockfile, Ansible via `uv sync`.
3. **Persistence**: JSONL history and image store.
4. **Local backend** on the Mac Mini: Ollama + Draw Things/mflux. Benchmark on
   real hardware before committing to the Pi rewrite. Check RAM first: 16 GB is
   the floor, 24 GB+ is comfortable for Flux dev.
5. **FastAPI service** exposing the core over HTTP for both clients.
6. **Pi device UI**: pygame/framebuffer + GPIO, replaces Streamlit + Chromium.
7. **Rust Pi client** (optional, after 6 and the HTTP contract is stable).

Phases 1 and 2 first; 3 alongside; 4 and 5 next; 6 and 7 only once local
generation is proven.
